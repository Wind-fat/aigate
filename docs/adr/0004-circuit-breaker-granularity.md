# ADR-0004 熔断粒度：按 provider，不按 model

- 状态：已采纳
- 日期：2026-11

## 背景

有了 fallback 之后，主供应商持续故障会怎样？每个请求仍然先去打一次死掉的供应商，
等超时，再切备用。fallback 保证"能用"，但不保证"不浪费"：延迟翻倍，且失败请求同样计入
你的调用量（很多供应商连 5xx 都计费）。

熔断器解决的是这件事：连续失败 N 次后，直接跳过该供应商，冷却期后放一个探测请求。

## 决策

**按 `provider` 计数**，不按 `provider:model`。

| 方案 | 优点 | 为什么不是它 |
|---|---|---|
| 按 provider | 供应商故障通常是整站级（区域故障、欠费、限流） | ← 采用 |
| 按 model | 能精准隔离单个模型下线 | 一个模型挂了往往意味着整个账号/区域有问题，按 model 会让熔断迟钝 |
| 按 key | 最精确 | 状态爆炸，且 key 轮换频繁，热路径上无意义 |

阈值与冷却：`AIGATE_CIRCUIT_THRESHOLD`（默认 3 次连续可重试失败）、
`AIGATE_CIRCUIT_COOLDOWN_S`（默认 30 秒）。

**只有可重试错误才计入熔断**。4xx 不计入：那是调用方的问题，把它算进供应商健康度
会让一个坏客户端把整个供应商摘掉。

## 后果

- 状态在进程内，多副本时各自判断 —— 见 README「已知限制」。集群级熔断需要 Redis
  （与限流器同一套基础设施，Stage 3 再考虑）。
- **fallback 必须指向另一家供应商**。如果主备是同一个 provider 名，主候选失败会把
  熔断打开，备用候选随即被跳过，等于没有 fallback。演示数据里 `mock` / `mock-alt`
  是两个独立实例，就是为了让这条语义能被测试验证。
- 半开期只放一个探测请求，避免冷却结束瞬间把所有流量砸回一个刚恢复的供应商。
