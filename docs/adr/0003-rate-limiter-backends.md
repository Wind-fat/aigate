# ADR-0003 限流后端：进程内令牌桶 vs Redis

- 状态：已采纳
- 日期：2026-11

## 背景

配额必须在**调用上游之前**生效，否则"限流"只是记账。这要求一次原子的
"读余额 → 判断 → 扣减"，且在多副本部署下必须跨进程一致。

## 决策

同一接口两套实现，由 `AIGATE_RATE_LIMITER` 切换：

| 后端 | 适用 | 实现 | 代价 |
|---|---|---|---|
| `memory` | 开发、测试、CI、单机演示 | `dict` + `asyncio.Lock` 的令牌桶 | 多副本时每个副本各有 60 rpm，实际是 60×N |
| `redis` | 生产 / 多副本 | Lua 脚本单次往返内完成 refill + 扣减 | 多一个组件；Redis 挂掉要决定"放行"还是"拒绝" |

## 为什么用 Lua 而不是先 GET 再 SET

两个并发请求都会读到 "还剩 1 个 token"，然后都扣减成功 —— 限流在最需要它的
高并发时刻失效。Redis 的 Lua 脚本在服务端原子执行，且用 `TIME` 取服务器时钟，
避免多副本机器时钟漂移导致令牌凭空多出或永久卡死。

## 后果

- 默认 `memory`：`git clone && make test` 不需要 Redis。
- 多副本部署必须切 `redis`，并给 Redis 配置持久化之外的独立监控（限流器不可用 =
  网关不可用，这是新的单点）。
- 令牌桶（而非固定窗口）是刻意的：固定窗口在窗口边界允许 2× 突发，对下游是真实伤害。
