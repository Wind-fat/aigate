# ADR 0012 · 多副本：限流与熔断共用 Redis，其余保持无状态

## 背景

早期三个决定都是为了「一台机器也能跑」：

- 限流器有 `memory` / `redis` 两种后端（ADR-0004）；
- 熔断器**只有内存实现**，"每个副本各有一套看法"；
- 会话 cookie 无状态，靠每请求查 `status` 吊销。

一旦部署两个副本，前两条立刻变成事故：

| 现象 | 根因 |
|---|---|
| 项目设了 60 RPM，实际能打 120 | 内存令牌桶按进程算，额度 = `N × rpm` |
| 供应商已经 502 两分钟，流量还在往上打 | 每个副本要各自失败 `threshold` 次才开闸 |
| 控制台问"这家现在是开着还是关着"，答案取决于负载均衡打到哪台 | 状态没有共享视图 |

## 决定

**熔断器也做成可插拔，并与限流器共用同一个后端开关。**

```python
circuit_backend: str = ""          # 空 = 跟随 rate_limiter
```

`main.py` 启动时按 `rate_limiter`（或显式的 `circuit_backend`）构建：

- `memory` —— 单进程。开发、CI、单副本安装用它；测试也用它（不依赖外部服务）。
- `redis` —— 共享。两个副本看到同一个判决；冷却结束后用 `SET NX` 只放**一个**探测请求进去。

实现细节与取舍：

1. **不加 Lua**。限流器用 Lua 是因为它必须原子（一枚令牌只能被一个请求拿走）；熔断器是
   启发式开关，两个副本同时记一次失败丢掉一次自增，最多让它晚一次开闸——不值得为此引入
   脚本依赖。写在模块 docstring 里，避免后人以为是漏写。
2. **状态带 TTL**（`cooldown × 10`）。没有 TTL 的话，一个已经恢复的供应商会因为"很久没人
   调用"而永远停在 agents 记录里；TTL 太短则会让死掉的供应商在空闲期看起来健康。
3. **Redis 起不来就退回内存**（`reset_to_memory()`），并打一条 warning。一个本地熔断器
   比没有熔断器好：至少单机能自保。**不**让服务启动失败——网关没有熔断也能接客，
   但起不来就一个请求都进不来。

## 仍然不共享的东西

说清楚边界，避免把"多副本"当成已经完全解决：

| 组件 | 多副本一致性 | 说明 |
|---|---|---|
| 限流 | ✅ Redis | Lua 原子 |
| 熔断 | ✅ Redis | 见上 |
| 会话 | ✅ 无状态 | HMAC cookie + 每请求查 `status`，任一副本都能验 |
| 语义缓存 | ⚠️ 库内（PG） | 多副本共享同一个 PG 就一致；SQLite 多副本不成立 |
| 记账队列 | ⚠️ 各自 spool | 每个副本自己的 spool 文件与批量写；`request_id` 去重保证不重复记账 |
| 预算判断 | ⚠️ 库内聚合 | 并发跨副本时可能同时越过 100%（最多超额一次请求的成本） |

预算这一条是刻意的：为了"绝对不超额"而给每次请求加分布式锁，代价远大于一次请求的误差。

## 验证

- `tests/test_circuit.py`：两个「副本」（两个实例共享一个假 Redis）——A 判定死亡，B 立刻同意；
  冷却结束只放一个探测请求；成功清空共享状态。
- `scripts/audit.py`：对**真进程**跑 43 项检查（端点矩阵、边界参数、错误信封、并发写、页面可达）。
- 本机没有 redis-server，所以 `redis` 后端只验证了协议层（假客户端），
  没验证真实 Redis 的网络行为——这一点写在 README 的已知限制里。

## 后果

- 好处：把 `AIGATE_RATE_LIMITER=redis` 打开就能多副本，不需要改任何业务代码；
  单副本继续用内存实现，零外部依赖。
- 代价：Redis 成为多副本部署的硬依赖；它挂了会退化成"每个副本各自限流"，而不是拒绝服务。
