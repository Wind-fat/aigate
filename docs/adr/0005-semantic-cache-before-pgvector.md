# ADR-0005 语义缓存：先暴力余弦，pgvector 后置

- 状态：已采纳
- 日期：2026-11

## 背景

ADR-0001 说过向量用 pgvector。但落地时本机没有 Docker，也就没有 PG：
写一套 `pgvector` SQL 意味着**提交一段没人跑过的代码**——在作品集项目里，
未验证的代码比没有这段代码更糟，因为它会被当成"实现过"。

## 决策

1. 向量以 JSON 存在 `semantic_cache_entries.embedding`，检索用 Python 暴力余弦。
2. 检索入口收敛在 `SemanticCache.lookup()` 一个函数里，换索引只改这里。
3. 每次 L2 检索最多扫 `AIGATE_CACHE_MAX_SCAN`（默认 2000）条，按 `created_at desc` 取最近。

## 为什么现在这样是合理的

| 规模 | 暴力余弦成本 | 结论 |
|---|---|---|
| 1 千条 × 256 维 | ~0.5 ms | 完全可接受 |
| 1 万条 | ~5 ms | 仍可接受（相对于 800ms 的上游延迟） |
| 100 万条 | ~500 ms | 必须换 pgvector / Qdrant |

也就是说：**这个决定的失效点是规模，不是正确性**。而在作品集规模下，
正确性 + 可测试性 >> 索引性能。ADR-0001 的结论没错，只是提前了。

## 阈值不是常数

同一个 0.92，对 bge-m3 是合理的，对 hash embedding 会让缓存永不命中（同义句只有 0.71）。
所以阈值挂在 embedder 上（`Embedder.recommended_threshold`），配置项留空即用校准值。
这是一个**接口设计问题伪装成参数问题**的典型例子：把阈值放进全局配置，等于假设
所有 embedding 模型的相似度分布一样。

## 后果

- 换 pgvector 时只需：加 `vector(1024)` 列 + 迁移 + 改 `lookup()` 的查询。上层（v1_chat、
  测试、bench 脚本）零改动。
- 必须定期清理过期条目（当前靠 `expires_at` 过滤，物理删除留给 Stage 4 的定时任务）。
- L2 命中可能比不缓存更慢，README 实测表里如实写了。缓存不是免费的加速器。
