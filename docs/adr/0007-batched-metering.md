# ADR-0007 批量记账：赢了尾部，输了中位数

- 状态：已采纳（有代价，且代价被记录）
- 日期：2026-11

## 背景

同步记账（每请求 2 条 INSERT + 1 条 UPDATE + 1 次 COMMIT）让 SQLite 的单写者锁成为吞吐天花板：
20 并发下 ~42 rps，客户端 p95 1500ms，而网关自身只有 34ms —— 94% 的时间在排队等写锁。

## 决策

请求路径只把一条 `UsageEvent`（纯 dataclass）塞进有界队列，由后台 worker 合并成一批、
一次事务写入。

三条不可协商的规则：

1. **绝不丢账**。队列满或 worker 未启动时，退回**同步内联写**并承担延迟。
   慢请求可以恢复，丢账单不能。
2. **不跨队列传递 ORM 对象**。事件里的字段都是请求已经算好的值，避免已关闭的 session 泄漏进 worker。
3. **不改变账目语义**。同样的行、同样的 Decimal、同样的列；改变的只是「何时 COMMIT」。

第二批优化：worker 内部从 ORM `session.add()` 改成核心 `insert()` executemany。
逐对象走 unit-of-work 约 1ms/对象，100 条就是 100ms 的**事件循环阻塞**。

## 实测（20 并发 × 200 请求，SQLite，同一台机器）

| 实现 | rps | 客户端 p50 | p95 | p99 | 网关内 p50 |
|---|---|---|---|---|---|
| 同步（基线） | 42.3 | **238 ms** | 1500 ms | 3216 ms | **34 ms** |
| 批量 + ORM add | 41.6 | 412 ms | 687 ms | 862 ms | 98 ms |
| 批量 + 核心 insert | **51.4** | 365 ms | **597 ms** | **711 ms** | 80 ms |
| 批量 + 小批次(50/20ms) | 45.9 | 415 ms | 630 ms | 749 ms | 90 ms |

## 结论：这是一个真实的权衡，不是纯赢

- **尾部大幅改善**：p95 −60%，p99 −78%，错误 0（同步版本每次还有 2–4 个 `database is locked` 的 500）。
- **中位数变差**：238 → 365ms。原因不是「批量更慢」，而是批次的 CPU 工作（构造 100 行、
  编译 executemany）仍然跑在事件循环上，形成一个周期性的 head-of-line 阻塞。
- **吞吐 +22%**，但没有数量级变化 —— 说明 SQLite 单写者仍是硬约束，批量只是把
  「每请求一次锁竞争」换成「每批一次」。

## 后续（按代价排序）

1. 把写批次挪出事件循环（线程执行器或独立写进程）——直接消除 p50 的回退。
2. 换 PostgreSQL + asyncpg 连接池——单写者约束消失，届时批量与不批量的差别会小很多。
3. 预算聚合（每请求一次 `SUM(cost_cny)`）改 TTL 缓存或物化计数器——它随月内行数线性变慢。

## 为什么还是采纳了

因为对网关来说，用户投诉的是「偶尔卡 3 秒」，不是「每次都慢 130ms」；而且错误率从
有 500 变成 0，这是正确性问题，优先级高于延迟数字。**代价写在这里，不藏在 README 的
漂亮数字后面。**
