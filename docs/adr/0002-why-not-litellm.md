# ADR-0002 为什么不用 LiteLLM 全量接管

- 状态：已采纳
- 日期：2026-11

## 背景

LiteLLM（62k★，活跃）已经实现了多 provider 转发、成本计算、预算与虚拟 key。直接用它，
两周就能拿到一个"看起来完整"的网关。自己写是不是重复造轮子？

## 评估

| 能力 | LiteLLM | 本项目是否需要自己实现 |
|---|---|---|
| 多 provider 转发 | 完备 | 否——本项目只覆盖 3 家，用一个 OpenAI 兼容适配器足够 |
| usage / 错误归一化 | 完备 | **是**——这是"换模型不改代码"的技术根据，必须自己掌握 |
| 预算与配额 | 有（虚拟 key） | **是**——归因口径要按 team/project 三级，与自有表结构绑定 |
| 语义缓存 | 有（较新） | **是**——缓存正确性（tenant 隔离、prompt 版本）是本项目的核心论点 |
| 记账与账单 | 有 | **是**——账必须落在自己的表里，能和财务口径对齐 |
| 控制台 | 有（通用） | **是**——产品叙事的载体 |

## 决策

**不整包依赖，但明确参考其设计。** 具体边界：

1. 转发与重试策略参考 LiteLLM 的实现思路，代码自写（约 150 行，可控）
2. 三家供应商收敛到 `OpenAICompatibleProvider`——因为行业已事实统一在 OpenAI 协议上
3. 所有与组织绑定的部分（配额口径、账单表、缓存 key、门禁）自己实现

## 后果

- README 与面试必须**主动说明**这一点，不能说"从零造了个网关"。
- 若未来接入非 OpenAI 协议的供应商（如 Anthropic 原生 API），只需新增一个 `BaseProvider`
  子类，路由与记账层零改动——这正是抽象层的价值证明。
- 代价：短期功能覆盖不如 LiteLLM 全（如 function calling 透传延后）。这是有意识的取舍。
