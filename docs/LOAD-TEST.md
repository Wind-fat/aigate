## What is measured

`POST /v1/chat/completions` → `chat-default` → offline `mock` provider (10 ms fixed sleep, no
network). Each level sends **600** requests from **N** keep-alive connections (one
request in flight per connection — exactly N concurrent clients) over loopback HTTP.

The upstream is a mock on purpose: the subject is the gateway's admission control, metering
and persistence, not a vendor's latency.

## Why the client is not httpx

The first run used `httpx.AsyncClient`. Against a bare FastAPI `/health` it measured 241 rps
(p50 27.7 ms) at N=8, while N keep-alive sockets measured 2776 rps (p50 1.4 ms) on the same
host — the client library was the bottleneck, not the gateway. The script therefore speaks
HTTP/1.1 over `asyncio` streams (stdlib), one persistent connection per client.

## Reading the numbers

- A 503 **with** `Retry-After` is the designed fast-fail when the pool is exhausted: refuse
  now instead of hanging for 30 s. A 503 **without** `Retry-After` is a bug and fails the run.
- `MissingGreenlet` would mean sync attribute access on an expired ORM instance inside the
  async request — the failure that silently drops metering rows. Zero is the only OK value.
- SQLite admits one writer, so throughput flattens well before the pool is exhausted; the
  PostgreSQL run is in `docs/PG-VERIFY.md`.

## What the numbers say (and the two defects they exposed)

**1. 503 从 N=16 开始就是预期内的拒绝，不是故障。** 池容量是 15 条连接，而一个请求会
**占着连接走完整个请求**（鉴权、预算 SUM、provider 调用、`_persist`、`_maybe_shadow` 各查一次）。
SQLite 只有一个写者，8 并发时单请求已经被拉长到 ~129 ms，15 条连接只能撑住 ~15 rps；
N=16/32 的那部分请求在池里等超过 1 s，于是拿到 503 + `Retry-After: 1`。
`5xx = 0`、`MissingGreenlet = 0`、`database is locked = 0` 是本轮最重要的三个 0：
准入失败是可解释的，500 和计费丢失不是。

**2. `synchronous` 只在一条连接上生效（已修）。** 修复前 `init_db()` 里设一次
`PRAGMA synchronous=NORMAL`；`journal_mode` 是文件属性，设一次够，但 `synchronous` 是
**连接属性**，每条新连接都回到 FULL(2)。压测时池里新建的连接全在 FULL 下跑 —— WAL 里
每次 commit 都 fsync，而 SQLite 只有一个写者，锁竞争恰好发生在 commit 上。
`db.py` 改成在 `set_engine()` 里挂 `connect` 事件，逐连接设 PRAGMA；
回归用例 `tests/test_sqlite_pragmas.py` 断言三条并发连接的 `synchronous` 都是 1
（修复前实测 `[1, 2, 2]`）。

**3. 方言判断看错了地方（已修）。** `init_db()` 原来用 `settings.is_sqlite` 决定是否发
`PRAGMA`。`set_engine()` 允许显式传 URL（测试、脚本、切换数据库），此时 settings 仍停在默认
SQLite 上，于是把 `PRAGMA journal_mode=WAL` 发给了 PostgreSQL —— 真 PG 上启动就是
`syntax error at or near "PRAGMA"`。现在按 `engine.dialect.name` 判断，见
`docs/PG-VERIFY.md` 的复现记录。

命令：`.venv/Scripts/python.exe scripts/loadtest.py --db-url "postgresql+asyncpg://postgres:@127.0.0.1:55299/aigate_load" --levels 8,16,32 --requests 600`

PG 上 503 明显少于 SQLite（N=16 只有 5 个），但 p50 并没有变快 —— 单请求在 PG 上多出
约 90 ms，且 8 并发时按 ~90 ms 一档线性排队。**已定位**（`docs/PERF-PG.md`）：不是 SQL 慢，
是**一条新连接的建立要 p50 119 ms**，而请求路径上每个请求都在多要一条连接
（`_maybe_shadow()` 在没配影子模型时也会新开 session），8 并发 = 16 条需求 > 池的 15 条，
溢出连接被回收 → 热点上反复建连。`log_connections=on` 下 320 个请求建了 27 条连接，
改完后 12 条；`shadow_ms` P50 26 → 5 ms，client P50 143.5 → 107.5 ms。
另外两点订正：`pg_stat_activity` 当时看到「连接被复用」是因为快照取在池热/空闲时刻，
连接授权次数说明热点上一直在重建；「单请求 +90 ms」在空库热池下复现不出来
（顺序 PG 31.0 ms vs SQLite 31.3 ms，client 口径），能复现的是「需要新建连接时一档
~85–130 ms」，因此上面的 PG 数字仍只能当**上界**看。
